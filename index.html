STEP 1 OF 7 · THE PROBLEM

A documentation job that punishes humans for being human

Before schedules can migrate to a new planning platform, every project file must be fully documented — every local and enterprise custom field, every formula, every pick-list, every task value.

Done by hand, each Microsoft Project file means opening it in the right server environment, walking its local and enterprise custom fields, exporting several outputs, and checking them — 7 to 10 minutes of careful clicking per file. Multiply by a thousand-plus files and it's weeks of person-time spread across program teams, doing the exact kind of repetitive work where tired people make quiet mistakes: a missed column, a wrong environment, a value pasted one row off. Nobody notices at file 400. The migration inherits the error.

THE DESIGN LAW, SET ON DAY ONE

Data is never allowed to be wrong — it only ever takes longer. Every bulk-export mechanism in this tool must prove itself against an independently built cell-by-cell export before it is trusted, and every failure must land somewhere a person will see it. Speed is negotiable. Correctness and visibility are not.

STEP 3 OF 7 · WHY YOU CAN TRUST IT

The verification engine

The bulk capture isn't trusted because it was tested once — it's re-proven at the start of every batch against an independent method built a completely different way.

STEP 1 · FIRST FILE OF EVERY BATCH — EXPORT IT TWICE
BULK CAPTURE · SECONDS PER FILE

Applies a saved table in Microsoft Project and captures the grid column by column through the clipboard — the one copy operation Project genuinely supports.

CELL-BY-CELL · MINUTES PER FILE

Reads every value one cell at a time over the automation link — the plodding, proven baseline that has never been wrong.

BOTH OUTPUTS GO HEAD-TO-HEAD
STEP 2 · COMPARE EVERY CELL

Every cell of the first file, from both exports — not a sample. On a typical file that is 50,000+ comparisons covering every local and enterprise field, so the two independent methods must agree perfectly before speed is allowed.

THE VERDICT GATES THE WHOLE BATCH
STEP 3 · THE VERDICT
PERFECT MATCH → BULK CAPTURE EARNS THE BATCH

Every file after the first uses bulk capture, still guarded per file: row-count checks, selection-coverage checks, and spot checks re-read straight from the source.

ANY MISMATCH → CELL-BY-CELL RUNS INSTEAD

The whole batch runs cell-by-cell instead and says so, by name, in the log. Output can take longer — never wrong.

And six standing guards, active on every run:

01WRONG-ENVIRONMENT PROTECTION

Nine server environments on one machine. The tool verifies the signed-in account before touching any file, and cached field definitions are stamped with environment and tool version — a stale or foreign cache refuses itself and rescans.

02READ-ONLY, ALWAYS

Every source file opens read-only and closes without saving. The tool is physically incapable of writing into a schedule.

03NEVER LAUNCH BLIND

Project is only ever launched into a chosen, verified account — never while another copy is running, never into a sign-in screen it can't see. If Project is frozen, the tool stops and names the fix.

04WATCHDOG + SKIP-AND-CONTINUE

A file that stalls Microsoft Project for five minutes can be cancelled alone. One bad file costs one file, not the batch.

05SELF-CHECKING OUTPUTS

Workbooks are validated against Excel's own file rules at save time — table naming, cell-size limits, accidental formulas — and a standalone checker can audit every output on disk.

06NO SILENT FAILURES

Every skipped field, retry, fallback, and refusal is named — on screen, in the plain-language LOG tab, and in the raw TECHNICAL record each workbook carries.

STEP 4 OF 7 · THE ENGINEERING STORY

Three fights this tool won

The interesting part of automation is never the happy path. These are real, from the build's decision log.

WAR STORY 01The export map from the wrong world▶

The bulk export originally called Microsoft Project's built-in export engine, pointed at a saved export map. For weeks, every run failed a different way — and every failure looked like a normal bug:

SYMPTOMWHAT IT LOOKED LIKEWHAT WAS TRUE
Unicode crashwrong text encodingwrong map
1 column exportedwrong delimiterwrong map
Garbled header bytesbinary file formatwrong map
0 columns exportedExcel unavailablewrong map

Each "fix" was correct for the symptom it targeted, and none of them helped — because the organization runs several separate Project Server environments, and the map being called belonged to a different one. It resolved by name without any error, exported a file every time, and the file could never contain the right data. The layer that was broken never appeared in any error message.

LESSON, NOW A STANDING RULE

A theory is only ruled out for the exact combination you tested. Varying one input at a time while the broken input stays constant will "eliminate" every innocent variable and leave the guilty one standing.

WAR STORY 02The clipboard that only spoke a private language▶

Plan B was the obvious one: select the whole grid in Project, copy, read the clipboard. Instrumentation told the truth — after a full-grid copy, the clipboard holds MPDB, Project's private format, and no text at all. Not a fluke, not flaky: structurally never going to work. Every bulk route Project appears to offer was tested and closed the same way — the export engine ignored requested formats and once quietly re-saved an entire project as an 8.8 MB binary blob mid-diagnosis.

The breakthrough came from a hand test, not from code: copying one column at a time posts real text. Project supports the copy everyone actually does by hand, and only that one. So the capture was rebuilt to walk the applied table column by column — reading each column's field name from the grid itself, verifying the selection covers every task before copying, retrying the occasional empty clipboard, and detecting the end of the table explicitly. ~36 columns land in about 24 seconds.

LESSON

When automation fights the platform, stop and watch what a human does successfully — then automate that, guards and all.

WAR STORY 03The bug my own safety net caught▶

The column walker shipped with a safety cap: stop after 80 columns, set when the widest table had 36. Then the local-fields table turned out to be 132 columns wide. The walker stopped at 80 and the last 52 columns exported blank — a classic silent truncation, the exact class of bug that poisons a migration.

It never shipped wrong data. The first-file comparison found 19,954 mismatched cells, refused the bulk capture, and ran the whole batch cell-by-cell instead. Output correct; only speed lost. The fix made the failure honest as well as fixed: the cap is now an explicit refusal with a named reason, never a quiet stop — and a test scenario pins it that way forever.

LESSON

Design the net before you need it. The verification layer isn't overhead — it's the thing that turns your own future mistakes into delays instead of corruption.

STEP 5 OF 7 · RUNNING WITHOUT A BABYSITTER

Unattended by design. Accountable by default.

Batch runs start from a cold machine and end with receipts — proven live, end to end.

  1. Launches Microsoft Project itself into the chosen server environment — never blind, never a second copy — and waits out the sign-in.
  2. Verifies the signed-in account before touching a single file. Wrong account: stop, with instructions. Nothing half-done.
  3. Processes each file — captures, verifies, writes the dictionary workbook and both CSV exports into a date-stamped folder.
  4. Archives as it goes — each source file is moved into its output folder only after processing finishes cleanly.
  5. Survives the bad file — names it, turns the bar red, moves on. The end-of-run summary lists every failure by name.
  6. Cleans up after itself — closes what it opened, restores every setting it touched, and quits Project if it launched it.
THE PAPER TRAIL, PER FILE

Every file produces three outputs: a task-level CSV of all 130 local custom fields, a task-level CSV of every enterprise custom field, and a data-dictionary workbook whose four tabs — Data Dictionary, LOOKUPS, a plain-language LOG of every warning and decision, and the raw TECHNICAL run record — mean each file's evidence travels with the file.

THE OPERATING REALITY

Developed and verified against a live Microsoft Project environment and real aerospace and defense program schedule files — dozens of live test runs a day, each one read back through its run logs. Deployed in a locked-down environment; every safeguard above was proven against real files, not toy data.

Before any update went live: 40 offline failure scenarios replayed against a simulated Microsoft Project, every one required to end in "refuse and fall back" — never wrong output.

STEP 7 OF 7 · WHAT THIS DEMONSTRATES

Designed. Developed. Deployed.

The point isn't that a script exists. It's what it takes to make automation trustworthy enough for production data.

/ 01Designed

  • Safety laws before features: never wrong (only takes longer) · no silent failures · never launch blind · sources stay read-only.
  • Verification architecture: independent dual export + cell-by-cell comparison gating every batch.
  • Failure design as a first-class feature — every refusal has a name and a fallback.

/ 02Developed

  • A ~4,000-line Python engine driving Microsoft Project over COM automation, plus a point-and-click GUI.
  • A 40-scenario offline test suite that simulates Project itself — every dangerous case must end in "refuse and fall back."
  • 52 documented working sessions with a decision log: what was tried, what was ruled out, and why.

/ 03Deployed

  • In production use against real aerospace and defense program files across three server environments, cold-start to clean exit.
  • Deployed and verified in a locked-down environment, with updates installed through a one-click updater and confirmed through run logs.
  • Operator-proofed: no console, no command line — double-click launchers and plain-language logs.

My role: the architecture, the safety laws, the trade-offs, and every field test — working with AI as my engineering partner for implementation.
